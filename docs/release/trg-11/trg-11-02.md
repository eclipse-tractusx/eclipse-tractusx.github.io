## Why

Eclipse Tractus-X products are released together. Whether they work together is verified in the
[E2E testing phase](/docs/oss/release-process#e2e-testing-phase) of each release: typically three weeks, on one shared
integration environment, with a daily meeting. A change that breaks the hand-over between two products is found there,
weeks after it was merged, and somebody has to work out which change caused it.

[TRG 5.09](../trg-5/trg-5-09.md) made every product prove on each pull request that its Helm chart installs and starts,
and names itself "the base for future e2e tests". This TRG is that next step. Every product proves on each pull request
that it keeps a promise **the way a partner uses it**: through its public interface, in a running dataspace.

The test is written in one common format, a TCK project for
[Eclipse Tractus-X TestLab](https://github.com/eclipse-tractusx/tractusx-testlab), so that:

- a contributor can read the E2E test of any product without learning that product's test framework,
- release management and adopters can run the same test against any deployment,
- tools can find the test, because the repository metafile says where it is.

The visible effect: a broken hand-over shows up as a red check on the pull request that caused it, and the release
dashboard can show for every product whether its E2E test exists and passes.

## Description

This TRG applies to the **leading repository** ([TRG 2.04](../trg-2/trg-2-04.md)) of every product. It does not apply to
repositories with `repoCategory` `support` or `special` in their metafile ([TRG 2.05](../trg-2/trg-2-05.md)). The other
repositories of a product are covered by the test in the leading repository.

A *TCK project* is a folder with a manifest `index.yaml` (`kind: tck`) and one YAML file per test, as described in the
[TCK syntax reference](https://eclipse-tractusx.github.io/tractusx-testlab/tck-syntax/).

### 1. Where the project lives

- 1.1 The leading repository **MUST** contain at least one E2E test as a TCK project.
- 1.2 The project **SHOULD** be located in the folder `tck/e2e`. Another folder **MAY** be used. In both cases the folder
  **MUST** be declared in the metafile (see section 2).
- 1.3 The manifest **MUST** declare `metadata.license: Apache-2.0`, and every file of the project **MUST** carry the
  license and copyright header of [TRG 7.02](../trg-7/trg-7-02.md).
- 1.4 The project **MUST NOT** contain addresses, participant identifiers or credentials of an environment. Such values
  **MUST** be declared as variables or `infrastructure.*` references and supplied when the test runs.

### 2. The metafile

- 2.1 The `.tractusx` metafile of the leading repository **MUST** list every E2E test under the key `e2eTests`.
- 2.2 Each entry **MUST** have a `name`, a `path` and a `workflow`.
- 2.3 `path` **MUST** be the folder that contains the manifest `index.yaml`, relative to the repository root.
- 2.4 `workflow` **MUST** be the path of the GitHub Actions workflow that runs the test (see section 3).

```yaml
e2eTests:
  - name: "Digital Twin Registry E2E test"
    path: "tck/e2e"
    workflow: ".github/workflows/e2e-test.yml"
```

### 3. The workflow

- 3.1 The workflow **MUST** run, for the declared project, `testlab validate`, then `testlab compile`, then
  `testlab run` on the package that was compiled.
- 3.2 The workflow **MUST** run on every pull request that targets the default branch, and on every push to the default
  branch. It **SHOULD** also offer `workflow_dispatch`.
- 3.3 The run **MUST** be executed against a deployment that includes the product. The deployment **SHOULD** be created
  inside the runner as the Eclipse Tractus-X developer toolbox: the
  [Tractus-X Umbrella](https://github.com/eclipse-tractusx/tractus-x-umbrella) chart with a small dataspace
  configuration, in memory, so that no shared environment and no secret is needed. It **SHOULD** deploy the product as built from the change under test.
- 3.4 A workflow that runs against a shared or permanent environment **MUST** take every address and credential from
  repository secrets and **MUST NOT** run for pull requests from forks.
- 3.5 The version of TestLab the workflow installs **MUST** be pinned.
- 3.6 The workflow **SHOULD** call the reusable workflow described under [Golden path](#golden-path). A workflow of the
  product's own **MAY** be used if it fulfils 3.1 to 3.5.

### 4. What the test must cover

- 4.1 The project **MUST** contain at least one **positive** test: it obtains a result from the product through the
  product's public interface, in the way a consumer of the product obtains it. For a product that is reached through a
  connector, that way is catalog request, contract negotiation and access through the data plane.
- 4.2 The project **MUST** contain at least one **negative** test: something the product must refuse or must not find,
  with the specific answer that is expected.
- 4.3 Every test **MUST** contain at least one validation of a value the product returned. A test that only checks that
  a call was answered does not fulfil 4.1 or 4.2.
- 4.4 A test that creates resources **MUST** remove them in its `teardown`, and **MUST** pass when it is run twice in a
  row against the same deployment.
- 4.5 Where a standard defines the shape of an answer, the project **SHOULD** validate the answer against that JSON
  schema.
- 4.6 The manifest **SHOULD** list in `metadata.standards` the standards whose behaviour the tests check.

### 5. What counts as passing

- 5.1 `testlab validate` and `testlab compile` **MUST** end with exit code 0.
- 5.2 `testlab run` **MUST** end with exit code 0: every test passed. A skipped test does not count towards 4.1 or 4.2.
- 5.3 For a release, the latest run of the workflow on the commit that is released **MUST** have passed.
- 5.4 A test **MUST NOT** be removed or marked `skippable` to make the workflow pass, unless an issue in the repository
  explains why and is linked from the change.

### How this can be checked automatically

| Check | Rule |
|-------|------|
| `.tractusx` has `e2eTests` with at least one entry that has `name`, `path` and `workflow` | 2.1, 2.2 |
| `<path>/index.yaml` exists and declares `kind: tck` | 1.1, 2.3 |
| The file named in `workflow` exists and triggers on `pull_request` and on `push` to the default branch | 2.4, 3.2 |
| The package compiled from `<path>` contains at least two tests and at least one validation per test (`testlab inspect --json`) | 4.1 to 4.3 |
| The latest run of that workflow on the default branch concluded with success | 5.1 to 5.3 |

## Golden path

The tutorial [E2E tests for Tractus-X products](https://github.com/eclipse-tractusx/tutorial-resources/tree/main/e2e-testing)
takes a team from "here is your product" to a pull request in about one hour. It provides:

- a template project to copy,
- a worked example for the Digital Twin Registry that passes in GitHub Actions,
- a reusable workflow that creates the dataspace inside the runner. A product repository calls it like this:

```yaml
name: E2E test

on:
  pull_request:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  e2e:
    name: E2E test
    uses: eclipse-tractusx/tutorial-resources/.github/workflows/e2e-test.yml@main
    with:
      tck-directory: tck/e2e
```

The reusable workflow has two jobs. "Validate and compile" needs nothing but Python. "Run in Eclipse Tractus-X
developer toolbox" creates a cluster in the runner, deploys two connectors, two wallets, a Digital Twin Registry, a BDRS and an
IssuerService, issues the participants' credentials and runs the package.

A product that the developer toolbox cannot deploy yet sets `run-in-toolbox: false`. It then fulfils 3.1 only for validate and
compile, and **MUST** document in its README how and where the test is run.

## Open points of this draft

- **Number and category.** This draft uses 11.02 in a new category "Testing and Quality", next to the code coverage TRG
  proposed in [#1396](https://github.com/eclipse-tractusx/eclipse-tractusx.github.io/pull/1396). The number 11 is also
  proposed for "Generative AI" in [#1569](https://github.com/eclipse-tractusx/eclipse-tractusx.github.io/pull/1569). The
  TRG editors assign the final number.
- **Metafile key.** `e2eTests` extends [TRG 2.05](../trg-2/trg-2-05.md) and the
  [metafile documentation](https://github.com/eclipse-tractusx/sig-release/blob/main/docs/metadata_file.md). The name and
  the three fields are a proposal. If it is accepted, TRG 2.05 and that documentation need an update.
- **Home of the reusable workflow.** It is proposed in `tutorial-resources` together with the tutorial. `sig-infra` or
  `tractusx-testlab` may be the better place once the TRG is active.
- **Testing the change itself.** The reusable workflow deploys released images unless the caller passes its own Helm
  values. Rule 3.3 asks for the image built from the change as a **SHOULD** for that reason.
- **Mandatory date.** To be set with release management, after the first products have a test.
