Contributor Journey (Videos)

Prefer watching over reading? Follow the Contributor on their way into the Eclipse Tractus-X community. The eight short episodes (about 2 minutes each) summarize the most important parts of this Developer Hub. Episodes 1–4 cover your way from the first accounts to becoming a committer, episodes 5–8 dive into the rules, KITs, documentation and security. Watch them in order, or jump directly to the topic you need.

Episode 1: Get your keys​

Before you can contribute, you need three "keys": a GitHub account, an Eclipse Foundation account and the signed Eclipse Contributor Agreement (ECA).

You will learn how to:

  • create a GitHub account and enable two-factor authentication (2FA)
  • create an Eclipse Foundation account with the same email address
  • sign the Eclipse Contributor Agreement (ECA)
  • link your GitHub ID in your Eclipse profile

Read more: Getting started

Transcript

Welcome to the Tractus-X Contributor Journey! In episode 1, we help our Contributor get the keys to the project. Meet the Contributor. They have a great idea for Eclipse Tractus-X! Everyone can read the code, the docs and the issues. But to actually contribute, you need three keys.

Key number 1: a GitHub account. Sign up on github.com, turn on two-factor authentication, and add the email address you will also use for Eclipse. There's your first key!

Key number 2: an Eclipse Foundation account. Register at accounts.eclipse.org, and use the very same email as on GitHub. If you contribute for your employer, use your company email. Key number 2, done!

Key number 3: the Eclipse Contributor Agreement, or ECA. Sign it once, and your contributions can be accepted into the project. That's all three keys!

One last thing. Open your Eclipse profile and add your GitHub ID under Social Media Links. Now both accounts know each other. And there it is. With all three keys, the gate opens! You can now open issues, comment and create pull requests. Welcome to the project!

Quick recap. GitHub with 2FA, an Eclipse account with the same email, the signed ECA, and your linked GitHub ID. All details are on the Getting Started page. Next time: say hello to the community and open your first pull request!

Episode 2: Say hello & your first PR​

Join the conversation, open an issue and get your first pull request through the two-step review.

You will learn how to:

  • join the developer mailing list, Matrix and the open meetings
  • open an issue for bugs and feature ideas
  • create a pull request in the Tractus-X repository (commit messages, copyright headers, DEPENDENCIES file)
  • pass the two-step review: content review and committer review

Read more: How to contribute · Code reviews

Transcript

Welcome back to the Tractus-X Contributor Journey! In episode 2, our Contributor says hello to the community and opens a first pull request.

First, join the conversation. Subscribe to the developer mailing list tractusx-dev. It's the official channel for questions, news and discussions. For quick chats, join the Tractus-X rooms on Matrix. And drop by an open meeting, like the monthly new-joiner office hour or the community office hour on Fridays.

Found a bug, or have an idea for a new feature? Open an issue! Issues keep development open and transparent, and they document why things change.

Ready to code? Then create a pull request. Do it in the Tractus-X repository, so the whole community can follow along. Write meaningful, descriptive commit messages. Add copyright headers to new files and keep the DEPENDENCIES file up to date.

Every pull request gets reviewed, in two steps. Step 1: a content review by a qualified person, for example from the product team. Step 2: a committer does the final review for open source governance. Address the feedback. Once everything is fine, the committer merges your pull request. And that's it! Your first contribution is merged. Welcome to the Tractus-X community!

Quick recap. Join the mailing list and Matrix, open an issue, create your PR in the Tractus-X repository, and pass the two-step review. All details are on the How to contribute and Code reviews pages. Next time: jump on the Tractus-X release train!

Episode 3: The release train​

How a feature gets into a quarterly Tractus-X release — from the feature issue to end-to-end testing.

You will learn about:

  • the quarterly release cadence and the R{YY}.{MM} naming
  • feature issues and the Release Planning Board
  • Alignment Day and Open Planning Day
  • development along the Tractus-X Release Guidelines (TRGs)
  • deployment to the integration environment and end-to-end testing

Read more: Tractus-X Release Process

Transcript

Welcome back to the Tractus-X Contributor Journey! In episode 3, our Contributor wants to bring a new feature into a Tractus-X release.

Tractus-X ships a new release every quarter: in March, June, September and December. Each release is named after its year and month, for example R26.03 for March 2026. One release cycle takes about three to four months.

To get on board, you need a ticket: a feature issue. Use the feature template: describe the feature, acceptance criteria, dependencies, and how it will be tested and documented. Then add it to the Release Planning Board on GitHub.

Do you have open questions, or dependencies on other features? Add the label "open question" at least three days before Alignment Day. On Alignment Day, the community resolves open questions and cross-feature dependencies.

Next stop: Open Planning Day. Your feature must be in the backlog, with a contributor and a committer assigned, a topic set, and a complete template. Together, the community prioritizes the features and assigns them to a release milestone.

All aboard! Your feature moves to "In Progress". While you build it, follow the Tractus-X Release Guidelines, the TRGs. Committers review your pull requests, and regular product meetings track the progress.

Before the release, the features are deployed to the integration environment. Then comes end-to-end testing: typically three weeks, with daily syncs. And finally, the release leaves the station!

Quick recap. Quarterly releases, a feature issue as your ticket, Alignment and Open Planning Day, build along the TRGs, and test on INT. All details are on the Release Process page. Next time: level up and find out how to become a committer!

Episode 4: Level up​

From contributor to official project contributor, committer and project lead.

You will learn about:

  • the Eclipse project roles and their GitHub permissions
  • how to become an official project contributor
  • what merit means and how the committer election works
  • the rights and duties of committers and project leads

Read more: Eclipse project roles · Committer Election Process

Transcript

Welcome back to the Tractus-X Contributor Journey! In episode 4, our Contributor levels up and finds out how to become a committer.

Eclipse projects have different roles, and you grow into them step by step. With an Eclipse account and the signed ECA, you are already a contributor. You can open issues, comment and create pull requests.

Next level: official project contributor. Reach out to a committer or project lead on Matrix. They add you to the project, and you accept the GitHub invitation. Now you have the triage role: label, assign and close issues and PRs, set milestones and request reviews.

To become a committer, you need to show merit. That means: you have already done the work of a committer. For example: significant contributions and reviews, valuable bug reports, TRG compliance tickets, and helping the community.

When you are ready, you and a committer prepare your nomination together. The committer nominates you on the Eclipse project page, and the developer mailing list is informed automatically. For one week, the committers vote. Then the project leads and the Project Management Committee decide. After some paperwork with the Eclipse Foundation, you're in!

Congratulations, committer! Now you can push code, review and merge contributions, nominate new committers, vote in elections and help plan the project. And one day, the committers might even elect you as a project lead. Project leads have extended rights and responsibilities and make sure everyone follows the rules.

That's the core of the Contributor Journey. Get your keys, say hello, jump on the release train, and level up. All details are in the Tractus-X Developer Hub. Next time: open the rulebook!

Episode 5: The rulebook​

A tour through the Tractus-X Release Guidelines (TRGs) — the road signs on your way to a release.

You will learn about:

  • what TRGs are and how they are grouped into ten topics
  • the documentation (TRG 1) and Git (TRG 2) requirements
  • container (TRG 4) and Helm (TRG 5 and 6) guidelines
  • licenses, headers and IP checks (TRG 7)
  • how new TRGs are drafted and released

Read more: Tractus-X Release Guidelines

Transcript

Welcome back to the Tractus-X Contributor Journey! In episode 5, our Contributor opens the rulebook: the Tractus-X Release Guidelines.

TRG stands for Tractus-X Release Guidelines. They define the default workflows and requirements for contributing to, maintaining and running Tractus-X products. Think of them as the road signs on your way to a release.

The guidelines are grouped into ten topics. Documentation, Git, Kubernetes, containers, Helm, artefacts, open source governance, security, UX/UI and KITs.

TRG 1 is about documentation. Every repository needs a README and, depending on the product, for example an install guide, a changelog, architecture and API documentation. TRG 2 covers Git: the default branch, the repository structure, and the .tractusx metadata file in every repository.

TRG 4 is all about container images: image tagging, base images, non-root containers, image signing, read-only file systems and multi-platform images. TRG 5 and 6 cover Helm charts: structure, versioning, resources, tests, upgradeability and released charts.

TRG 7 is about open source governance. Code is licensed under Apache-2.0, non-code like documentation and images under CC-BY-4.0. Add license and copyright headers, and run IP checks for your own and for third-party content. And TRG 8 keeps your repository secure. More about that in episode 8!

The rulebook is developed in the open, too. New guidelines start as drafts and are announced on the developer mailing list. Bigger ones become pre-releases first, with a date from which they are mandatory.

Quick recap. TRGs are the road signs for every product: documentation, Git, containers, Helm, governance, security and more. All details are on the Release Guidelines page. Next time: pack your KIT!

Episode 6: Pack your KIT​

What a KIT ("Keep It Together") is, how it is structured, how it matures and how to create a new one.

You will learn about:

  • what a KIT is and who it is for
  • the four KIT architecture categories and domains
  • the adoption, development and operations views
  • the maturity levels sandbox, incubating and graduated
  • the process to create a new KIT

Read more: KIT Framework · TRG 10 - KITs

Transcript

Welcome back to the Tractus-X Contributor Journey! In episode 6, our Contributor packs a KIT.

KIT stands for: Keep It Together. A KIT is an open-source toolbox with comprehensive documentation. It helps business people, solution providers and developers to build interoperable applications for Tractus-X dataspaces.

Every KIT belongs to one of four architecture categories: Dataspace Foundation, Industry Core Foundation, Cross-Industry Use Cases and Industry-Specific Use Cases. On top, each KIT has a domain, like sustainability or engineering.

Inside, a KIT is organized in views, for different readers. The adoption view explains the business value. The development view covers architecture, APIs and sample data. The operations view helps you run it. Every KIT also keeps a changelog, and every file has a CC-BY-4.0 license notice.

KITs grow in maturity. They start in the sandbox, move to incubating, and finally become graduated. To graduate, a KIT needs all required artifacts, and at least one Eclipse committer as code owner for maintenance. And a maturity level only changes with a release.

Want to create a new KIT? Discuss your idea, create a ticket in sig-release, and present it at Open Planning. Build the KIT and open a pull request to the Tractus-X website, with a changelog and the updated KIT master data. The responsible committer reviews it, and your KIT is published with the release.

Quick recap. Keep It Together: four categories, three views, three maturity levels and one clear creation process. All details are in the KIT Framework documentation and in TRG 10. Next time: write the docs!

Episode 7: Write the docs​

Documentation is a contribution, too: how to contribute to this website.

You will learn about:

  • how the website repository is organized
  • how to preview your changes locally
  • where to put videos and other large files
  • which license notice your pages need
  • what happens when you open a pull request

Read more: Website Admin Guidelines · Repository README

Transcript

Welcome back to the Tractus-X Contributor Journey! In episode 7, our Contributor writes the docs.

Documentation is a contribution, too! The Tractus-X website is built with Docusaurus. Its source lives on GitHub, in the repository eclipse-tractusx.github.io.

The content is organized in folders. docs for the Developer Hub, docs-kits for the versioned KIT documentation, and blog for the news. Add a markdown file, and it becomes a page with its own entry in the sidebar.

Before you open a pull request, preview your changes locally. Run npm install once, then npm start, and open localhost:3000. A markdown linter checks your style, also as a pre-commit hook.

Got videos, slides or other large files? Don't put them into the website repository. Upload them to the largefiles repository with Git LFS and link them from your page. Just like these videos!

Every page and every image needs a license notice. For documentation, that's CC-BY-4.0. Then open your pull request. The website build is verified automatically, and you get a preview link to see your changes live.

Quick recap. Pick the right folder, preview locally, put large files into largefiles, add the license notice and open your pull request. All details are in the Website Admin Guidelines and the repository README. Next time: safety first!

Episode 8: Safety first​

How to report vulnerabilities and which security tools keep Tractus-X repositories safe.

You will learn about:

  • how to report a vulnerability privately
  • how committers handle security advisories
  • the TRG 8 security tools: CodeQL, KICS, TruffleHog, Trivy and Dependabot
  • how scan findings are handled
  • how to harden containers (TRG 4)

Read more: TRG 8 - Security · Security policy

Transcript

Welcome back to the Tractus-X Contributor Journey! In episode 8, it's safety first: security in Tractus-X.

Found a security vulnerability? Please do not report it in a public GitHub issue! Instead, open the Security tab of the affected repository and click "Report a vulnerability". In severe cases, you can also contact the Eclipse Foundation security team.

Committers handle the report confidentially, in a draft security advisory. They follow the Eclipse Foundation vulnerability reporting policy until a fix is ready.

To catch problems early, TRG 8 defines security tools for Tractus-X repositories. CodeQL analyzes your code. KICS checks infrastructure as code, like Helm charts. TruffleHog searches for leaked secrets. Trivy scans your container images. And Dependabot keeps your dependencies up to date.

The scans run regularly, at least once a week, and many also on every pull request. Findings show up in the GitHub security dashboard. Dismiss a high finding only with a clear justification.

Secure containers matter, too. Following TRG 4, containers run as non-root and use read-only file systems wherever possible. Questions? Join the Tractus-X security room on Matrix.

Quick recap. Report vulnerabilities privately, let the TRG 8 tools scan your repository, and harden your containers. All details are in TRG 8 and in the security policy. Thanks for following the Contributor Journey. See you in the community!
